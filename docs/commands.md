# Commands and outputs

This page describes each `crucible` command, the files a run writes, and what the leak checks mean. Run `crucible` with no arguments for the same list in the terminal.

## Commands

```text
crucible run experiment.yaml [--no-archive]
crucible prepare experiment.yaml
crucible start <run-id>
crucible status <run-id> [--watch|--json]
crucible stop <run-id>
crucible judge <run-id>
crucible capture <run-id>
crucible report <run-id>
crucible archive <run-id> [--to <dir>] [--build-dir <dir>]
crucible clean <run-id> [--yes]
crucible init [<path>]
crucible list [--json]
crucible series [<name>]
crucible check [<dir>...]
crucible prune [--older-than <days>] [--yes]
crucible doctor [<agent>...]
crucible config
crucible ui [--port N] [--no-open]
```

`crucible run` performs the full sequence — prepare, produce, judge (or capture, with no judge), report, archive — and stops at the first failure. It archives the run at the end and prints the path, unless the experiment sets `archive: false` or the command carries `--no-archive`. Archiving copies the producer workspaces, so it happens before `cleanup: automatic` removes them; `crucible report` on its own only writes the three report files. `start` verifies the agent CLIs and, when the sandbox is on, probes the profile before launching; the results land in `checks.json`. Preparation freezes one pristine copy of the source and one context per arm under the run directory, and `start` always builds producer workspaces from those copies — so relaunching a failed or stopped arm is just `crucible start` again, with no separate retry step. Each workspace holds the copied project under `source/`, the frozen skills under `.context/`, and the scrubbed home under `.runtime/`; the producer starts in `source/`, as a real session would, and the prompt names the other two by absolute path. A producer that hits its timeout after changing the source is not a failure: the arm counts as complete with whatever output was on disk at the cutoff, and the report carries a warning. One that times out without touching the source fails like any other crash, so `crucible start` can relaunch it.

`crucible stop` stops whichever agents are at work, the producers or the judge. An agent whose process has already died is marked stopped rather than refused. Stopping producers marks the run stopped, so `crucible start` relaunches them; stopping only the judge leaves the outputs ready for another `crucible judge`.

Producers hold an idle-sleep assertion until they exit. `status` reads local state and process information only; it does not contact an agent or reveal the assignment. It shows each producer's elapsed time against its timeout budget and flags `near timeout` past 80% of it. Once judging starts, the judge appears as its own row, tracked the same way and against its own timeout. `--json` emits the same view as machine-readable JSON for the agent driving the run, and `--watch` ends once no agent is at work.

The judge takes the pictures. Before it starts, the runner serves each output's folder as static files on a port the kernel picks, fetches one file back and compares the bytes with the judged copy, and names those URLs in the judge's prompt; the servers live in the runner process and close when the judge exits. A judge that once started `python3 -m http.server 8801 &` with its output discarded never learned the bind had failed and scored an earlier run's leftover pages, which is why the judge is told not to start static servers of its own. While it inspects the outputs it starts anything that needs more the way that output's own instructions say — a Vite project through its dev server, from a scratch copy on a port it has confirmed free — and takes full-page desktop (1440 wide) and phone (390 wide) screenshots, full height but never wider than the viewport, so a deck with its slides laid side by side shows the slide on screen, of up to four pages per output, the finished experience first, into its own workspace under the anonymous letters, with a `shots/index.json` naming them. Once the verdict is in, the runner copies them into the run's `shots/` folder under the arm labels and rewrites the index with those labels, so the report and the archive show the pages the judge scored. A run with no judge has no one to start its outputs, so the runner opens the files itself; `crucible capture` below describes that. An output that is only Markdown is rendered by the judge on a plain page and pictured that way, marked `rendered: "markdown"` in the index. An image output such as an SVG is pictured first centred and scaled up on a plain page, so its leading picture is not a small icon in an empty corner. A page that would not run gets no picture and the judge's error in the index; a picture the judge names outside its own folder for that letter, or one that is missing, is recorded the same way and never copied. Nothing fails over a missing picture — the index records why — and a judge that wrote no index leaves `skipped` set, which the report shows as a note. Playwright's browsers are the ones installed under `~/Library/Caches/ms-playwright`; a `PLAYWRIGHT_BROWSERS_PATH` pointing at a cache that holds no browser is ignored, so a judge started from inside a sandboxed agent session still finds Chromium. The Playwright the judge loads is Crucible's own, linked into its workspace beside the packages of any configured `nodeModules`. Its prompt claims Playwright only when `require("playwright")` resolves from that workspace, and says whether its Chromium is installed. `crucible doctor` checks both: that Chromium is installed for Crucible's Playwright version, and that a judge workspace loads Playwright under the sandbox.

The judge sees the outputs as letters, `A` to `F`, in a random order. It writes two files: `verdict.md`, its full reasoning, and `verdict.json`, the same verdict as data — winner, confidence, a 0–10 score per rubric item with its weight, a guess at which output is the control arm, the one produced without any candidate or override, and a one- or two-sentence summary. A one-arm run is told to score its single output against the rubric instead of picking a winner, and is asked for no control guess. The runner checks the JSON's shape and refuses a judgment that lacks it, so a run is never reported without a structured result.

`crucible report` then seals the run in three forms from that one verdict: `result.json` (the verdict with the arms revealed and named by their labels, plus each arm's total, the winner's margin over the runner-up, each arm's time and tokens, warnings, and the shot index), `report.md`, and `report.html`, a self-contained page with the score table, one screenshot panel per arm, and the judge's prose. Reporting can be repeated; it changes nothing but those three files.

The winner is the judge's own choice, revealed. The runner never rewrites a verdict from the totals, so on the rare run where the judge names an arm that did not score highest, `margin` is negative and the report warns which arm scored higher. With one arm there is no runner-up, so `margin` is null and the report reads as a score rather than a win.

`result.json` records the arms in run order under `arms`, the skill environment under `environment`, and each arm's producer and the judge as objects — `producers.<label>` and `judgeAgent`, each with `agent`, `model`, and `effort`, plus an arm's `settings` path, the names of its extra environment variables, and its `setup` command when it had them. Each arm's cost keeps the agent's own `usage` keys untouched and adds `tokens` (input, output, cacheRead, cacheWrite, whatever the agent called them). Each adapter collects its agent's usage from the transcript — Claude's input-side counts are summed once per API call, since its final result event does not add them up, while its output count is every result event's added up, since a message reports its own before streaming ends and a headless run can print more than one result; output written by subagents is not counted, because their messages carry only the provisional figure from the start of the message — and `src/cost.ts` is the one place those counts are turned into `tokens`. The runner reports time and tokens, never dollars, because a price table goes stale as soon as a provider changes its rates.

`crucible list` shows the runs still in progress or never archived, then every archived result with its series; `--json` prints the same view as the store API returns it (see below). `crucible series <name>` tallies the reported runs of one series — wins per arm, and the mean total and mean tokens per arm — and `crucible series` alone lists every series. Totals compare only within a series, where the rubric and task are the same.

`crucible ui` serves a dashboard on `http://127.0.0.1:8300/` (or `--port`) and opens it unless `--no-open` is given. It shows running tests with each agent's health (working, quiet, stalled, near its time limit), every archived result grouped into questions with their verdicts, and one run at a time with the arms' captures side by side, the criteria scores, the judge's reasoning and control guess, and time and tokens. A capture opens that arm's page live in a full-window viewer, on the captured slide, where it runs and takes keys as it would in a tab; the viewer lists every HTML page and SVG the arm produced, switches arms on the same page, and has a phone-width frame. A page that needs a server or a build to run says which of its files did not load. It reads the same results and runs folders as the other commands, refreshes itself, filters results by search, verdict, series, and the date of their newest run, and can delete an archived run, an idle run record, or several selected results at once after confirmation. It listens on loopback only and answers only its own page. Output pages and reports were written by agents, so the dashboard serves them in a sandbox with an origin of their own, under a path whose token opens only their own archive entry or run record and changes each time the server starts. They cannot read or act on the dashboard or read another entry, and they can load from nowhere but this server and a few public CDNs for libraries and web fonts (unpkg, jsDelivr, cdnjs, Google Fonts, Fontshare), so they cannot send what they read anywhere; forms submit nowhere, and in the viewer a page cannot navigate away. Their URLs stop working when the server restarts. A script can read `GET /api/experiments`, the same scan the store API below returns. Its two actions need an `X-Crucible: 1` header; the dashboard sends it, and a web page cannot. `POST /api/reveal` takes `{"path": "<absolute path>"}`. `POST /api/delete` takes `{"items": [["<absolute path>", …], …], "dryRun": false}`: each item is deleted as `deleteEntries` deletes one selection, all of it or none, and the answer lists, in order, `{"deleted": [paths]}` or `{"error": "<why>"}` for each; with `dryRun` it removes nothing and says what each would take.

Run records live under the runs root (`~/.crucible/runs/<run-id>` by default); temporary producer workspaces live under the system temporary directory. `clean` removes only producer workspaces, preserving the run record, inputs, and transcripts even after archiving.

`crucible prune` sweeps up whole runs once the archive holds them. A run is a candidate when it is finished — judged, reported, or already cleaned — and `crucible archive` has saved it; a run that is prepared, running, failed, or stopped is never touched, and neither is the archive. `--older-than <days>` adds finished runs that were never archived and are older than that, which is how a run you decided not to publish leaves the disk. Without `--yes` it is a dry run: it prints each candidate with its date, state, whether it is archived, and its size on disk, then the total that would be freed. With `--yes` it removes each candidate's run record and its temporary workspace, the same workspace `clean` removes, and prints what went. Pruned runs are gone for good: the frozen inputs, transcripts, and full report stay only in the archived reading copy.

`crucible archive <run-id>` saves a curated entry in `<archiveRoot>/<name-slug>/` (or `--to <dir>`): a README of at most 200 words, `result.json`, `report.html`, optional `outputs/<label>/`, and comparison captures under `dependencies/shots/`. It refuses to publish an entry that fails the rules `crucible check` applies: those files and folders and nothing else, no symlinks or installed packages, and a representative screenshot for every arm whose output is visual, unless every capture of that arm records why the page could not be pictured. `crucible check` runs the same rules, plus the checks a reader applies to `result.json`, over every entry already archived (or each `<dir>` given) and exits non-zero on any problem, including a target that is missing or not a folder. Files directly linked from the judge’s verdict are saved under `review-assets/` in the run and `dependencies/review-assets/` in the archive, with report links rewritten to the saved copies. Missing or private evidence becomes an explicit unavailable note and report warning; it is never replaced with a different capture. Frozen sources, rubrics, configuration, pinned skills, and transcripts stay in the run record.

Outputs contain the final files named by each screenshot’s `artifact` field, plus explicitly referenced local assets. `page` is the shared comparison label; `artifact` is the actual path relative to that arm’s output and may differ between arms. Multiple slides can refer to one HTML file; query and fragment suffixes are removed when copying it. Legacy indexes without `artifact` use `page` as the path. A missing selected artifact stops publication with an actionable error; correct the index from the verified output and regenerate the report before retrying. Without that index, changed HTML and Markdown files supply the entrypoints. Setup installs and ignored files are withheld first. For static build projects such as Vite, build each arm with relative asset URLs (for example `npm run build -- --base ./`), then use `crucible archive <run-id> --build-dir dist`. This explicit option selects a build directory relative to each producer workspace, including ignored build output; captured artifact paths must exist relative to that directory. It copies selected pages and referenced assets without executing build commands or changing the judge captures. Verify that the build matches the judged experience before publishing. Refreshing after cleanup reuses the archived pages without needing the build directory. Dynamic dependencies and server-backed applications may need manual packaging; the comparison captures remain available when there is no portable output.

Archive before cleaning producer workspaces. A later archive refresh updates the same entry and replaces obsolete captures. In the README it rewrites only the generated result between the `<!-- crucible:result -->` markers and keeps everything a reader wrote around them; a README with no markers keeps its text and gains the block at the end. When those notes take the README past 200 words, the refresh still goes ahead, prints a warning, and `crucible check` reports the entry until the notes are trimmed. The full task and result details remain in the report and structured result. Refreshes validate a replacement before replacing the existing entry and can use previously archived pages after cleaning.

## What the checks mean

Preparation scans for exact candidate slugs, titles, paths, aliases, and file hashes, and fails if any of them would reach another arm or the project instructions. A settings file that one arm alone names is that arm's material too, by its path and its content; one in the shared `producer` block belongs to every arm and so gives nothing away. It does not treat generic words from a slug as experiment terms: `frontend` is valid project text while testing `frontend-design`.

After the producers finish, an audit checks that the frozen contexts are unchanged and that no arm's candidate identity material reached another arm's output or logs. Audit findings are recorded as warnings in the report — they qualify the result rather than block it.

The judge also receives the untouched frozen source at `input/source`, so it can verify changes shared by every output; this is supporting material, not a competing output. The judge receives anonymous folders named A, B, C, and so on, each holding the arm's own work on top of the project as it was frozen: a directory the arm's setup step created is removed whole, with whatever the tool wrote into it afterwards, a frozen file the setup changed and the arm never touched is put back the way it was frozen, anything the project's `.gitignore` covers goes as well, and the report says how many files that withheld. Files that merely echo the frozen skill folder path are dropped from the judge copy; anything that still names a candidate is recorded as a warning. The assignment is revealed only in the report. This is procedural blinding, not perfect blindness: style, structure, naming, and visual polish can still reveal which output received a candidate.

One run is one sample. Agent output varies between runs, so treat a single verdict as evidence, not proof, and repeat the experiment when the decision matters.

## Reading the archive from code

`crucible/store` is the one reader of the archive and the run records, for a dashboard or a script. Everything in it is synchronous.

```ts
import { storeRoots, scanExperiments, readArchive, scanRuns, deleteEntries, checkArchive } from "crucible/store";

const roots = storeRoots();           // { archiveRoot, runsRoot }, resolved as the CLI resolves them
const scan = scanExperiments(roots);
// { root, blurb, live: { inFlight, unfinished }, questions, reportsOnly }
```

`storeRoots(environment = process.env)` reads the `CRUCIBLE_*_ROOT` variables, then the config file, then the defaults, so a consumer finds the same folders as `crucible list`. `questions` groups archived results by series, newest first, with each arm's win tally, mean total, and the question's `winner`: most wins, then the higher mean total. A run of one arm is scored rather than won, so it adds to no arm's wins, and a question made only of such runs goes to the higher mean total. `split` is true when that winner won no more than half the judged runs, so it leads without the runs agreeing; each run carries its `result`, preview images, and the output file that stands for each arm. Every question has a `key` for links: its series, or its only run's ID, with `@<entry folder>` appended when two run questions would share one. `readArchive(dir)` reads one archive entry and `scanRuns(runsRoot)` the run records alone. `reportsOnly` holds entries whose `result.json` is missing or untrustworthy, with the reasons in `issues`. `live` holds run records that are still producing or judging, and ones that stopped or finished without being archived, each with its agents' progress and health. `deleteEntries(roots, paths)` removes archive entries (with their run records) and idle run records, and refuses anything else, any path through a symlink, and any run with an agent still at work; a prepared run, or one whose agent's process has died, is idle. `deleteEach(roots, selections, { dryRun })` does the same for several selections at once, reading the store once, and returns `{ deleted }` or `{ error }` for each, so one refusal does not stop the rest. `resultIssues`, `entryIssues`, and `copiedRunIssues` expose the validation rules, and `experimentVisualPreviews` the preview choice.
